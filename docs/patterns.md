# Паттерны в Книгообмене

## Adapter (GoF)

`SQLAlchemyUserRepository`, `SQLAlchemyBookRepository` и
`SQLAlchemyExchangeRepository` реализуют те же ABC, что и InMemory-хранилища.
Они переводят вызовы предметного интерфейса в операции SQLAlchemy, а mapper-классы
преобразуют ORM-записи в dataclass и обратно. Сервисы не знают SQL и устройство
таблиц. Цена этого разделения — отдельные классы преобразования данных.

## Command (GoF)

`ExchangeCommand` хранит действие, ID заявки и сервис-получатель. Метод `execute()`
выполняет принятие, отклонение, отмену или подтверждение. Объект команды используется
и HTTP API, и обработчиками HTML-форм: допустимые действия описаны одним Enum,
а проверки статусов и прав остаются в `ExchangeService`. Очередь и история отмены
не добавлены, поскольку таких требований у проекта нет.

## Repository и Service Layer (Фаулер)

`src/repositories` отвечает за хранение, `src/services` — за проверки и правила.
FastAPI и Jinja вызывают существующие сервисы; правила обмена не дублируются
в обработчиках. `ServiceFactory` собирает сервисы одного HTTP-запроса и передаёт
всем хранилищам одну Session. Это обычная сборка объектов, а не отдельный GoF-паттерн.

## Unit of Work (Фаулер)

Session SQLAlchemy отслеживает все изменения HTTP-запроса. Зависимость
`get_services` открывает `Database.transaction()`, передаёт сервисы маршруту,
затем делает общий commit или rollback и закрывает Session. У зависимости задан
`scope="function"`: сохранение заканчивается до отправки ответа.

В HTTP-фабрике репозитории создаются с `commit_on_add=False`: добавление пользователя
и книги делает flush, а фиксация остаётся на Unit of Work. В CLI сохранён вариант
с commit при добавлении, использованный ранее. Нельзя смешивать эти режимы в одной
команде. Тесты проверяют откат добавленного пользователя и сбоя при резервировании
второй книги.

## Границы HTTP

Pydantic DTO лежат в `src/dtos/requests.py` и `responses.py`. Пароль, хеш и соль
не входят в ответы каталога и заявок. Пользователь восстанавливается из подписанной
cookie, для каждого запроса создаётся собственный UserService. Изменяющие запросы
проверяют CSRF-токен. JSON API получает его через `GET /api/session` и передаёт
в заголовке `X-CSRF-Token`; HTML-формы используют скрытое поле.

`/docs` содержит OpenAPI-схему. API и HTML используют один сервисный слой и БД.
